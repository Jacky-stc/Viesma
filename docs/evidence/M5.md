#### PostgreSQL 契約 spike 要驗證的假設

- 以同一角色 row lock 或等價的條件更新序列化寫入。相同 receipt key 先查原結果，再比對角色版本。版本更新、purse、堆疊、雙向換位與收據需同一 transaction 提交。驗證 `READ COMMITTED` 下與競爭寫入的隔離、失敗回滾及 lock 等待行為。
- 驗證 DB 可同時約束 bag slot 0..23、每 owner／位置唯一、全域裝備 instance ID 唯一、單一裝備位置、數量與 purse 範圍。滿包交換須在約束下成功，外部讀者只能觀察提交前或提交後。驗證 JSON metadata 比對與 canonical fingerprint 對應。
- 決定如何把原連線 epoch 與 requestId 映射到 durable play-session receipt key。驗證新 socket 只能重送同租約已記錄的請求，異 payload 被拒絕；查回舊收據時仍用目前角色快照。
- 以真資料庫注入提交前故障、COMMIT 確認遺失和並行重送。驗證 starter 初始化競爭只建立一次，提交後才能通知，非同步 I/O 結果排回固定 tick 套用，且權威版本不因重連、換圖或較晚回覆而回退。

本機記憶體保留角色有效期間的收據，另保留已接受而待完成的 EXP 目標。程序重啟後的保存、長連線收據成長與真機 Safari／Chrome 仍有待其後對應驗收。
